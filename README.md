# Future Era

**The GenX Era** — a site for the generation that stopped waiting for the future to arrive.

It has four pages (an intro, a creator showcase, a community page, and a career-blueprint tool) and one FastAPI backend that owns the career data.

---

## What is it

A small full-stack web project:

| Piece | Technology |
|---|---|
| Backend | Python 3.12, FastAPI, Uvicorn |
| Frontend | Plain HTML, CSS, vanilla JavaScript — no framework, no build step |
| Animations | GSAP 3.12.5 + ScrollTrigger, vendored locally |
| Data | One JSON file, served over HTTP |

There is **no AI or LLM anywhere** in this project. The career blueprint is generated by rule-based matching against the JSON — nothing calls out to a model provider, and there are no API keys.

### The four pages

- **Home** (`index.html`) — a scroll intro with an animated hero, then an "About" section.
- **Creators** (`creators.html`) — a scroll-scrubbed list of people, with a progress rail that fills as you scroll.
- **Community** (`community.html`) — four channels (Build Logs, Career Corner, Show & Tell, Questions), a slide of members suggested by shared interests and skills, and the latest discussions.
- **Career** (`career.html`) — the interactive part. Pick one of two paths, answer a few questions, and the page builds a career blueprint: what you can do, how to do it, and where to start.

The two career paths are **12th Pass Student** and **Graduated Professional**. The student path asks for a stream; the graduate path asks for a degree and filters the skill list to match it, with a free-text box for anything the filter leaves out.

Home, Creators and Community share one navbar. Career has no navbar at all — it uses a backlink instead — so it has no **Log in** button, but its footer still links to Community.

### Log in / sign up

Home, Creators and Community have a **Log in** button in the navbar that opens a popup with two tabs, **Log in** and **Sign up**. Signing up swaps the button for a chip showing your initial and a **Sign out** button; signing in after that puts you back where you started.

Community carries a **second** trigger — a *Log in* button in the closing call to action. So `initAuth()` collects every `[data-auth-open]` with `querySelectorAll` and walks the list twice: once to bind the click, once to hide the trigger on sign in. Binding only the first one left that second button silently dead, so `check_auth.py` fails if the lookup ever drops back to a single `querySelector` or the list is trimmed.

It is built on `<dialog>`, so the browser handles the backdrop and the Escape key. It is also plain DOM with no GSAP involved, so it works even when the animation library does not load.

The panel is styled from the home hero rather than picked separately, so the two never drift apart: same `lightseagreen` ground, same `lightcyan` text, same `#c8ff3d` accent, the title pairs Audiowide with Marck Script, the divider under it repeats the `.intro__rule` gradient, and everything is centred the way `.intro__inner` is. Two deliberate differences — the rule's track is `transparent` instead of `lightseagreen` (a lightseagreen line on a lightseagreen panel would be invisible), and the inactive tab text is a brighter `rgba(245,245,245,0.72)` than the hero's `0.55`, because white at 0.55 on that teal is hard to read.

The card is centred in the viewport, but not by the browser. The browser centres a `<dialog>` with `margin: auto` from its own stylesheet, and this project's `* { margin: 0 }` reset outranks the UA sheet — so the card landed in the top-left corner. The text inside it still looked centred, which makes it read as "the card is off to the side" rather than as a missing rule. `.auth__dialog` therefore sets `position: fixed`, `inset: 0`, `margin: auto` and `height: max-content` itself, and `check_auth.py` fails if any of the four goes missing.

**This is a front-end demo, not real authentication.** Accounts live in your browser's `localStorage` and passwords are hashed with SHA-256 before being written, so the password is not sitting there in readable text — but anyone with devtools can read the whole thing, nothing is verified against a server, and the accounts are per-device. Real accounts need routes in `Backend/main.py`.

There is no auth on the Career page: it has no navbar, so there is nowhere to put the button.

### Following people

The Community page has a horizontally scrolling slide of member accounts with a **Follow** button on each. Above it is a picker: pick a few of your own **interests** (10 of them) and **skills** (41, with a filter box), and the whole slide re-ranks itself on the spot.

The members live in `Backend/data/people.json` and are served, ranked, at **`/api/people`**:

```
GET /api/people?interests=ai,data&skills=python,sql
```

The score is deliberately plain arithmetic rather than anything clever, because there is no model anywhere in this project and the rule should be checkable by reading it:

```
both picked:  score = 60 x (interests you share / interests you picked)
                  + 40 x (skills you share / skills you picked)
one picked:   score = 100 x (that half you share / that half you picked)
neither:      no score at all
```

Interests are weighted higher than skills on purpose. Two people who both want to get into AI are worth introducing even when their toolkits do not overlap, whereas overlapping skills without a shared direction is just two people who happen to know the same thing. The number is shown next to the tags you actually have in common, so you can see the reasoning and disagree with it.

**Pick one half and it is scored out of 100 on its own**, rather than being marked down 40 points for the half you left blank. An axis you picked nothing on is an absence of evidence, not a mismatch, so its weight is handed to the axis that is. Without that, someone with interests picked and no skills would top out at 60 and a perfect match would be reported as 60% — a number that lies about the range the score is supposed to use.

The opposite case still costs what it should: a half you *did* pick and that nobody has is a genuine 0, not a shrug. Pick `ai` plus a skill no member lists and the best anyone can reach is 60.

**Picking nothing gives no score at all**, not a score of 0. A made-up zero would read as "no overlap" when it really means "we do not know yet", and it would push the whole list to the bottom as if every member were a bad match. With nothing picked the slide is ordered by follower count instead.

Two pieces of state stay in your browser:

- **Your tags** — one anonymous key, `future-era:profile`. They exist only to rank the slide and nothing in them is private.
- **Who you follow** — keyed by account, `future-era:follows:<your email>`, so two accounts on one machine do not share a list.

**This is still a front-end demo.** Following needs an account, so pressing **Follow** while signed out opens the log in popup rather than appearing to work and storing nothing. But the follow itself is never sent anywhere: no route records it, no other member can see it, and clearing site data loses it. Real follows need a write endpoint in `Backend/main.py` and a session to attribute them to.

**A successful sign in always lands on the home page.** Every time, from any page, on both the log in and the sign up form — there is no "first sign in only" branch, and signing out then signing in again goes home just the same. The confirmation says so before it happens ("Signed in. Taking you home.") so the pause is not a dead end, and the redirect is a relative `index.html` rather than an absolute `/index.html`, which keeps working if the site is ever served from a subfolder.

`check_auth.py` guards that with two structural checks rather than a list of flag names, because guessing names is worthless here — a first-time-only guard called anything at all slips straight past a denylist. So instead it requires that the navigation appears in **exactly one place** (a second call site is either redundant or one that also runs on page load, which with the session in `localStorage` would bounce the visitor off the home page forever), and that the guard in front of it asks **nothing except whether `location` exists**. A flag, a counter or a stored marker is a name-independent failure and gets rejected on sight.

**Every page loads `script.js?v=8`.** The `?v=` is there because this exact bug happened: the redirect was in the file on disk and the page still did not do it, because the browser was running its own cached copy of the script. Nothing in the project could tell the difference, because every check reads the file from disk rather than what a browser actually fetches. Bump the number in **all four** pages whenever `script.js` changes — `check_static.py` fails if it is missing, and fails if the four disagree, since one page left behind on an old version serves stale code for as long as that version stays cached.

`check_people.py` guards the data, the rule, and the half of the code that is easy to break silently: `people.json` is cross-referenced against `career_data.json`, the scoring properties are asserted (a member sharing nothing scores 0, one sharing everything scores 100, an unranked list has no scores), and the classes `script.js` puts on a card are checked against `style.css` — which `check_pages.py` cannot do, because the cards are built at runtime and never appear in the markup.

### Your profile

Click the signed-in chip in the navbar — the circle with your initial — and your profile opens: your name and email, the interests and skills you have picked, who you follow, and which groups you are in, with a count on each.

**Groups are real data.** The 5 of them live in a `GROUPS` registry at the top of `Backend/data/people.json`, each with a label and a line about what happens there, and every member belongs to at least one of them. `/api/groups` serves the registry with each group's member count; `/api/people` also puts each member's groups on their card, and carries the ranked **group suggestions** the Community page renders. A group is stored against your **account record** in `future-era:users`, not under a key of its own, so the groups travel with the account and signing out cannot strand them. The picker at the bottom of the popup is a row of real checkboxes, so it reports itself to a screen reader and works without JavaScript, and it writes through the same `setMyGroups()` the Community page's Join buttons use. See **Groups you might like** below for the ranking and what the Join button does.

**Your follower count is 0, and that is a real zero rather than a broken feature.** An account here is an email and a password hash in this browser, and nothing anywhere links one account to a member card, so there is no way to attribute another person's follow to you. Inventing a number, or borrowing the follower count off some member card, would both be a lie. So the popup says 0 and explains why next to it. Your following list, by contrast, is entirely real — it is the same `future-era:follows:<email>` list the Community page writes, just resolved to names. When a shared backend arrives, that single line is the only thing to change.

`check_profile.py` guards this, and it guards the *zero* as deliberately as the rest: it fails if the count stops being the literal `0`, and it fails if `initProfile` ever starts reading a `followers` field, because that field is a member's follower count rather than yours. It also checks the 16 `data-profile-*` hooks agree in **both** directions between the markup and the code, and on **every** page that has the popup — a hook missing from one of the three pages leaves a heading with nothing under it, and nothing else in the suite would notice.

### Groups you might like

The Community page has a **Groups** section under the member slide: all five groups, ranked, each with a Join button. Joining is entirely optional and reversible — nothing happens until you press Join, and pressing it again leaves.

**Five groups, not ten.** There were ten, and five of them had exactly one member — `model-lab`, `infra-watch`, `defenders`, `growth-room` and `ship-it`. A one-member group makes a poor suggestion: the card can only ever say "1 of 1 people here match you", which is a worse answer than no answer, and it ranked level with groups of seven as though it were a real community. Cutting them left the five that actually have people in them (7, 5, 4, 2, 2) and kept all 12 members in at least one. The five who lost their small group kept the other one they were in. Nothing in the code knows how many groups there are — the count, the member totals and the ranking all come from the registry — so putting one back is a data edit and nothing else.

**The ranking is the same rule the members are ranked by**, not a second guess at it. `score_tags()` in `Backend/main.py` is the one implementation; `match_people()` applies it to a person and `match_groups()` applies it to a group by scoring the union of that group's members' interests and skills. Weights, the 60/40 interest-to-skill split, the rescaling when you have picked only one axis, and the unranked-when-nothing-picked rule are all shared. Written out twice, a weighting is a weighting that will quietly drift, and the two lists sit on the same page claiming to rank you the same way.

Each card says **how many of the group's members match you**, and names up to three of them. The count is the claim; the names are the evidence. The three-name cap is applied in the browser as well as the server, because the card is laid out for three and a layout should not depend on an upstream limit staying where it is.

**A group you have not picked anything for says "not ranked" rather than showing 0%.** Zero is a real answer — it means your picks and that group share nothing. An unranked card means there is nothing to compare yet, and printing 0% there would say the second thing when you meant the first. With no picks at all, the order falls back to group size, which is honest and needs no scoring.

**Joining writes to the account record, in one place.** `setMyGroups()` in `script.js` is the only thing that writes `future-era:users[email].groups`, and both surfaces go through it: the checkbox in the profile popup and the button on the Community page. Written twice, the two would drift and the page would show you a membership you had just removed. It announces `future-era:groups-changed`, and the group list repaints, so ticking a box in the popup on one page changes the buttons on the other without a reload. `check_profile.py` fails if a second writer of the account record appears, or if the event stops being dispatched, because both failures are silent — the list just quietly stops agreeing with itself.

**A signed-out Join asks for an account rather than failing.** Nothing is written, and the login dialog opens — the same path a follow takes. A group joined to nobody is not a membership. The button also refuses any group id the page was not actually sent, since the id comes off the DOM and the list it would land in is stored on your account.

Nothing here is a network write. There is no endpoint to put a membership in, so — exactly like following — it lives in this browser's `localStorage` and travels with the account record. A shared backend would replace `setMyGroups()`'s body and nothing else.

## How it works

### One process, one port

`Backend/main.py` is the whole backend. It exposes four API routes and then serves the frontend as static files:

```
GET /api/health          -> {"status": "ok"}
GET /api/career-data     -> the entire dataset as JSON
GET /api/people          -> the community members, ranked against ?interests= and ?skills=, plus the groups ranked the same way
GET /api/groups          -> the group registry, with each group's member count
GET /                     -> the static site (Frontend/)
```

`/api/groups` is separate from `/api/people` on purpose. The profile popup is in the navbar on every page and needs the group names and blurbs, not twelve ranked cards or ten ranked groups, so the registry travels on its own route. `/api/people` additionally carries the **group suggestions** under `groups`, ranked by the visitor's own picks.

The group list on `community.html` does **not** fetch a second copy of `/api/people`. It renders from the payload the member slide has already fetched and announced (`future-era:ranked`). One request, one ranking, and no chance of the two lists disagreeing because a response arrived in a different order. `check_profile.py` fails if a second `fetch()` appears in the group code.

The static mount is registered **last** on purpose, so `/api/*` routes win over the catch-all. See `Backend/main.py:117`.

### The data lives in the backend

The career data used to be a JavaScript file the browser executed directly (`Frontend/career-data.js`). It now lives in `Backend/data/career_data.json` and reaches the browser over HTTP, so the backend genuinely owns it. The frontend fetches it once on the career page.

`Backend/data/career_data.json` holds 58 resources, 6 streams, 5 durations, 14 degrees, 10 interests, 12 hobbies, 41 skills, 12 roles and 4 phases. It is the single source of truth for the whole site — the skills, the roles, the phases, everything.

`Backend/data/people.json` holds the 12 community members **and the `GROUPS` registry of the 5 groups** they belong to. Both are deliberately cross-referenced: every member's interest and skill ids have to resolve to a real id in `career_data.json`, every member's role has to be a real role, and every group id a member lists has to exist in the registry — the same way, and for the same reason. A typo would not throw anywhere — the backend would return the member, the browser would render a chip with no label, and the match score would quietly count a tag that does not exist. `load_people()` and `load_groups()` raise at startup, and `check_people.py` and `check_profile.py` fail the build.

### Caching

The API response gets a strong SHA-256 ETag. When a browser already has the data it sends `If-None-Match` back and the server answers `304 Not Modified` instead of resending the body. `hash()` is deliberately not used here: Python salts `hash()` of a string per process, so a restart would change every ETag and throw away every browser's cached copy. See `Backend/main.py:57`.

Note that `load_data()` is cached in memory. After editing `career_data.json`, restart the server to pick up the change. HTML, CSS and JS edits are picked up immediately and need no restart.

### The animations

All animation lives in `Frontend/script.js` and uses a vendored copy of GSAP at `Frontend/vendor/`. Nothing loads GSAP from a CDN, so the animations survive an offline or firewalled machine.

`init()` runs ten independent sections:

| Function | Page | What it does |
|---|---|---|
| `initNav` | all | solid navbar on scroll, mobile menu, active link |
| `initAuth` | all but career | binds the log in / sign up popup |
| `initIntro` | home | hero timeline on load |
| `initAbout` | home | About section reveals on scroll |
| `initCreators` | creators | scroll-scrubbed rows, progress rail, hover effect |
| `initCommunity` | community | channel and discussion reveals, scrubbed rows, rail, hover effect |
| `initCommunityFollow` | community | the suggestion slide and the follow buttons |
| `initCareerHero` | career | hero reveal on load |
| `initCareer` | career | the blueprint, after the career data has been fetched |
| `initFooter` | all | footer year and reveals |

Each is wrapped in `step()` (`script.js:27`), which catches and logs a failure in one section instead of letting it take down the rest of the page's animations.

**Most of the animation is scroll-driven.** The hero plays on load, but the About section, the creator rows and the progress rail only move when they scroll into view. A page that looks static until you scroll is working correctly.

### The motion fallback

The stylesheet hides the hero at `opacity: 0` so GSAP can fade it in. That is a trap: if GSAP never runs, the text stays invisible forever and nothing throws to warn you.

So every animation is gated on `MOTION.ok` (`script.js:19`), which is false when either:
- the GSAP file failed to load, or
- the visitor asked for reduced motion (`prefers-reduced-motion: reduce`).

When it is false, `script.js` puts a `.no-motion` class on `<html>`, and the matching rules at the bottom of `style.css` restore everything to full opacity. The page then renders static instead of blank.

**This is the most common reason the site looks unanimated.** On Windows, turning off *Settings → Accessibility → Visual effects → Animation effects* makes every page static by design.

### The blueprint

`build()` in `script.js:697` runs entirely in the browser. It matches the typed role and chosen interests against the `ROLES` table, then assembles the blueprint from what it finds. If nothing matches it falls back to a generic version rather than showing an error. Nothing is submitted anywhere — the answers never leave the browser.

## Checks

The backend is pure Python — the checks use only the standard library, so nothing extra needs installing.

```powershell
cd Backend
.\.venv\Scripts\python.exe check_all.py
```

Seven checks run in order and it stops at the first failure:

| Check | What it verifies |
|---|---|
| `check_data.py` | every reference in the JSON resolves; no duplicate ids; every degree has skills; aliases are unambiguous |
| `check_people.py` | every member's interests, skills and role resolve; the match rule still scores 0-to-100 on either half alone or both; an unranked list stays unranked; a picked-but-unshared tag scores 0; **the same properties hold for the group suggestions, since they use the same weights**; every class `script.js` puts on a card is styled |
| `check_pages.py` | every CSS class used in the markup is actually styled; animated selectors exist |
| `check_static.py` | every id referenced by JS or CSS exists; links point at real files; scripts load in the right order; the cache buster is present and identical on all four pages; no leftover old markup |
| `check_anim.py` | all eleven animation sections still run, are gated on `MOTION.ok`, the looping tween is a `fromTo`, and nothing is left hidden at `opacity: 0` |
| `check_auth.py` | the navbar triggers, the dialog, the two forms and the CSS still agree; the password still goes through `digest()` before storage; a successful sign in lands on the home page from both forms, every time, with nothing in place to make it a first-time-only redirect |
| `check_profile.py` | every group in the registry has a label and a blurb, every member is in a group, no group is empty, and `/api/groups` counts agree with the file; the 16 `data-profile-*` hooks agree in both directions **on every page** that carries the popup; the follower count is still the literal `0` and nothing reads a `followers` field; **the group list on the Community page is registered in `init()`, reads the payload the slide already announced instead of fetching its own, repaints on sign-in and on a membership change, asks for an account before joining, and reports its state with `aria-pressed`**; the account record still has exactly one writer, and a joined group's border is actually a different colour from an unjoined one |

`check_anim.py` is the interesting one. Animation bugs are silent — a tween that never gets wired up, or an element hidden at `opacity: 0` that nothing ever reveals, produces no error, just a page that quietly stops moving. That check exists to catch exactly that class of problem.

`check_auth.py` guards the same class of problem for the login modal, which is worse there because the modal is duplicated across two files. Renaming one `data-auth-*` hook, or a field id that `script.js` reads, does not throw — the button just quietly stops doing anything. It reads the minimum password length off the comparison itself rather than off the message beside it, so renaming the error text cannot sneak past it.

`check_people.py` has one more job that only exists because of how the member cards are written. They are built in `script.js` at runtime, so `check_pages.py` never sees them: a class name misspelled in the template would leave an unstyled card and every other check would stay green. It also checks both ends of the `future-era:open-auth` and `future-era:session` conversations, because renaming one side of a `window` event leaves the other side listening to nothing and says nothing about it.

## Troubleshooting

**`.\.venv\Scripts\python.exe : ... is not recognized`**

You are in the wrong folder. The prompt must end in `Future-Era\Backend>` — the venv lives inside `Backend`, not `Future-Era`. Run `cd Backend` first.

**`Python was not found; run without arguments to install from the Microsoft Store`**

You typed bare `python`, which hits the Windows App Execution Alias shim. Use the full relative path `.\.venv\Scripts\python.exe` instead.

**The site loads but the career page shows "Could not load the career data"**

The API is unreachable. Confirm the server window is still open and you are on port 8000.

**The suggestion slide says "Could not load the member list"**

Same cause, same fix. That section is the only thing on the community page that needs the API, and it says so in the slide rather than leaving an empty space.

**The page is blank or the animations do not run**

Open <http://127.0.0.1:8000/diag.html>. It checks the protocol, the GSAP file, reduced motion and the fallback in your browser, and tells you which one is the problem. Turn off *Settings → Accessibility → Visual effects → Animation effects* if reduced motion is the cause, then hard-refresh with `Ctrl+Shift+R`.

**Everything looks static even though GSAP is fine**

That is expected. Scroll the page. Only the hero animates on load.

**Never open the `.html` files directly**

Double-clicking `index.html` gives a `file://` URL. The `fetch("/api/career-data")` call in `script.js` is root-relative and cannot work there, so the career page breaks. Always go through `http://127.0.0.1:8000`.
