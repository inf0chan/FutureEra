# Future Era

**The GenX Era** — a site for the generation that stopped waiting for the future to arrive.

It has three pages (an intro, a creator showcase, and a career-blueprint tool) and one FastAPI backend that owns the career data.

---

## What is it

A small full-stack web project:

| Piece | Technology |
|---|---|
| Backend | Python 3.12, FastAPI, Uvicorn |
| Frontend | Plain HTML, CSS, vanilla JavaScript — no framework, no build step |
| Animations | GSAP 3.12.5 + ScrollTrigger, vendored locally |
| Data | One JSON file, served over HTTP |

There is **no AI or LLM anywhere** in this project. The career blueprint is generated by rule-based matching against the JSON — nothing calls out to a model provider, and there are no API keys.

### The three pages

- **Home** (`index.html`) — a scroll intro with an animated hero, then an "About" section.
- **Creators** (`creators.html`) — a scroll-scrubbed list of people, with a progress rail that fills as you scroll.
- **Career** (`career.html`) — the interactive part. Pick one of two paths, answer a few questions, and the page builds a career blueprint: what you can do, how to do it, and where to start.

The two career paths are **12th Pass Student** and **Graduated Professional**. The student path asks for a stream; the graduate path asks for a degree and filters the skill list to match it, with a free-text box for anything the filter leaves out.

## How it works

### One process, one port

`Backend/main.py` is the whole backend. It exposes two API routes and then serves the frontend as static files:

```
GET /api/health          -> {"status": "ok"}
GET /api/career-data     -> the entire dataset as JSON
GET /                     -> the static site (Frontend/)
```

The static mount is registered **last** on purpose, so `/api/*` routes win over the catch-all. See `Backend/main.py:117`.

### The data lives in the backend

The career data used to be a JavaScript file the browser executed directly (`Frontend/career-data.js`). It now lives in `Backend/data/career_data.json` and reaches the browser over HTTP, so the backend genuinely owns it. The frontend fetches it once on the career page.

`Backend/data/career_data.json` holds 58 resources, 6 streams, 5 durations, 14 degrees, 10 interests, 12 hobbies, 41 skills, 12 roles and 4 phases. It is the single source of truth for the whole site — the skills, the roles, the phases, everything.

### Caching

The API response gets a strong SHA-256 ETag. When a browser already has the data it sends `If-None-Match` back and the server answers `304 Not Modified` instead of resending the body. `hash()` is deliberately not used here: Python salts `hash()` of a string per process, so a restart would change every ETag and throw away every browser's cached copy. See `Backend/main.py:57`.

Note that `load_data()` is cached in memory. After editing `career_data.json`, restart the server to pick up the change. HTML, CSS and JS edits are picked up immediately and need no restart.

### The animations

All animation lives in `Frontend/script.js` and uses a vendored copy of GSAP at `Frontend/vendor/`. Nothing loads GSAP from a CDN, so the animations survive an offline or firewalled machine.

`init()` runs six independent sections:

| Function | Page | What it does |
|---|---|---|
| `initNav` | all | solid navbar on scroll, mobile menu, active link |
| `initIntro` | home | hero timeline on load |
| `initAbout` | home | About section reveals on scroll |
| `initCreators` | creators | scroll-scrubbed rows, progress rail, hover effect |
| `initCareerHero` | career | hero reveal on load |
| `initFooter` | all | footer year and reveals |

Each is wrapped in `step()` (`script.js:27`), which catches and logs a failure in one section instead of letting it take down the rest of the page's animations.

**Most of the animation is scroll-driven.** The hero plays on load, but the About section, the creator rows and the progress rail only move when they scroll into view. A page that looks static until you scroll is working correctly.

### The motion fallback

The stylesheet hides the hero at `opacity: 0` so GSAP can fade it in. That is a trap: if GSAP never runs, the text stays invisible forever and nothing throws to warn you.

So every animation is gated on `MOTION.ok` (`script.js:19`), which is false when either:
- the GSAP file failed to load, or
- the visitor asked for reduced motion (`prefers-reduced-motion: reduce`).

When it is false, `script.js` puts a `.no-motion` class on `<html>`, and the matching rules at the bottom of `style.css` restore everything to full opacity. The page then renders static instead of blank.

**This is the most common reason the site looks unanimated.** On Windows, turning off *Settings → Accessibility → Visual effects → Animation effects* makes every page static by design.

### The blueprint

`build()` in `script.js:697` runs entirely in the browser. It matches the typed role and chosen interests against the `ROLES` table, then assembles the blueprint from what it finds. If nothing matches it falls back to a generic version rather than showing an error. Nothing is submitted anywhere — the answers never leave the browser.

## Checks

The backend is pure Python — the checks use only the standard library, so nothing extra needs installing.

```powershell
cd Backend
.\.venv\Scripts\python.exe check_all.py
```

Four checks run in order and it stops at the first failure:

| Check | What it verifies |
|---|---|
| `check_data.py` | every reference in the JSON resolves; no duplicate ids; every degree has skills; aliases are unambiguous |
| `check_pages.py` | every CSS class used in the markup is actually styled; animated selectors exist |
| `check_static.py` | every id referenced by JS or CSS exists; links point at real files; scripts load in the right order; no leftover old markup |
| `check_anim.py` | all six animation sections still run, are gated on `MOTION.ok`, the looping tween is a `fromTo`, and nothing is left hidden at `opacity: 0` |

`check_anim.py` is the interesting one. Animation bugs are silent — a tween that never gets wired up, or an element hidden at `opacity: 0` that nothing ever reveals, produces no error, just a page that quietly stops moving. That check exists to catch exactly that class of problem.

## Troubleshooting

**`.\.venv\Scripts\python.exe : ... is not recognized`**

You are in the wrong folder. The prompt must end in `Future-Era\Backend>` — the venv lives inside `Backend`, not `Future-Era`. Run `cd Backend` first.

**`Python was not found; run without arguments to install from the Microsoft Store`**

You typed bare `python`, which hits the Windows App Execution Alias shim. Use the full relative path `.\.venv\Scripts\python.exe` instead.

**The site loads but the career page shows "Could not load the career data"**

The API is unreachable. Confirm the server window is still open and you are on port 8000.

**The page is blank or the animations do not run**

Open <http://127.0.0.1:8000/diag.html>. It checks the protocol, the GSAP file, reduced motion and the fallback in your browser, and tells you which one is the problem. Turn off *Settings → Accessibility → Visual effects → Animation effects* if reduced motion is the cause, then hard-refresh with `Ctrl+Shift+R`.

**Everything looks static even though GSAP is fine**

That is expected. Scroll the page. Only the hero animates on load.

**Never open the `.html` files directly**

Double-clicking `index.html` gives a `file://` URL. The `fetch("/api/career-data")` call in `script.js` is root-relative and cannot work there, so the career page breaks. Always go through `http://127.0.0.1:8000`.
